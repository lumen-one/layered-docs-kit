# 参考：文档分层与写作规则

哪些文档受约束、层级怎么分、写作与维护的约定。

## 作用域

受这套体系约束的是面向人的文档：根级与子树说明、`docs/**`、模块 README、活跃决策记录、事故复盘、评审规则。

不受约束、各自按独立规则维护的：

- 代码注释与 JSDoc：契约写在声明处，由代码评审约束，本体系不规定注释文风。
- 机器消费的模板与提示词：逐字节被程序读取，改动等于改行为。
- 生成源：格式由生成器决定，只受新鲜度检查约束。
- 冻结归档区：只读，不编辑、不翻译、不移动，也不作为当前行为依据。

指令文件分层：根 `AGENTS.md` 只放每次会话都需要的规则；子树（`packages/`、`docs/`、决策记录目录等）各一份，只放对该子树生效的规则。根不复述子树，子树不复述根。每份 `AGENTS.md` 旁放 `CLAUDE.md`，支持软链接就指向同一文件，不支持就用同内容副本。

## 分层模型

位置是默认值，提案可以按项目调整，调整后以提案为准。

| 层 | 位置 | 职责 | 不写 |
|---|---|---|---|
| L0a 根级指令 | 根 `AGENTS.md` | 每次会话都需要的规则，短句加链接 | 教程、故事、长流程、可被链接的细节 |
| L0b 子树指令 | `packages/AGENTS.md`、`docs/AGENTS.md` | 只对该子树生效的规则 | 全仓规则 |
| L1 项目地图 | `docs/architecture.md` | 组成、核心模块、调用链、扩展点 | 类型定义、单模块细节、决策论证 |
| L2 模块契约 | 每个模块的 `README.md` | 配置、语义、限制、对外能力 | 别的模块的职责、生成内容、JSDoc 复述 |
| L3 参考手册 | `docs/reference/` 或 `docs/subsystems/` | 类型、API 语义、协议、数据结构 | 行为叙事、教程步骤 |
| L4 操作手册 | `docs/cookbook/` | 编号步骤与可验证结果 | 设计论证（链接决策记录） |
| L5 决策记录 | `docs/decisions/` 或 `.agents/notes/` | 为什么、放弃什么、怎么验证 | 迁移计划、验收清单、实现步骤 |
| L6 事故复盘 | `docs/postmortems/` | 事故经过与教训 | 通用规则（提炼后放 L7） |
| L7 评审规则 | `docs/patterns/` 或按领域拆页 | 要成立什么、怎么判定、谁批例外 | 类型语义、决策论证 |
| L8 生成式参考 | 源码旁或 `docs/generated/` | 脚本生成的清单、图、表 | 任何手工编辑 |
| L9 站点投影 | `website/` | 把 L1–L4 投影成对外站点 | 第二份可编辑内容 |

L1 与 L3 的边界：架构页按「包或服务在系统中的角色」组织，只到职责与调用关系；类型定义、字段语义、生成 API 归 L3。没有独立 `docs/reference/` 时，用 `docs/subsystems/<subsystem>/README.md` 一页一个子系统。

L8 有两种形态：同页生成区，由生成器把同一份数据写进两侧页面；整页生成，由生成器同时产出英文、中文与一致性记录。不存在「手工把结果复制到 `docs/generated/`」这第三种做法。

## L7 评审规则

一页通用缺陷类别，加每个领域一页，例如服务边界、并发与生命周期、持久化、客户端状态。每条写清「要成立什么、怎么判定、例外由谁批」。项目需要评审时再建，不必为凑层级而建。

## 一个事实一个家

同一规则、类型、命令、默认值只在一层定义，其他位置链接而不复述。判断归属时问「哪一层的工作就是维护这个事实」，而不是「哪个文件最近改过它」。

发现重复时：先确定归属页，把完整表述移过去，原位置改成一句链接；如果原位置有归属页没有的细节，先把细节补进归属页再删。

## 模块 README 契约

建议七节，前五节通常在检查范围内，后两节可选：

1. **Summary**：一段话说明读者能用它做什么，不写内部角色或实现身份。
2. **目录**：锚点链接。
3. **快速开始**：最短可用路径、主要代价、什么时候该选它。
4. **配置与使用**：配置表、默认值、限制。
5. **Known Limitations**：已知限制与失败模式。
6. **开发者视角**（可选）：整体设计与数据流，细节链接到代码或 L3。
7. **Dev Note**（可选）：草稿、未决方向、测量数据，标明「非权威」。

不写完整 API、不复述 JSDoc、不抄生成目录、不写别的模块的职责。

## 写作规则

- 主文档只描述当前状态，历史与被否方案进决策记录或复盘。
- 一段一个物理行，段落内不硬换行；表格、列表、代码块保持原格式。
- 相对链接指向当前文件；历史引用用 tag 或 PR 编号，不写 commit hash。
- 外部引用要能解析，或登记在信任清单里。
- 术语一词一义，首次出现给定义。
- 不用比喻替代精确名词。
- 把加粗留给改变行为的句子，强调才有稀缺性。
- 标题使用读者会搜索的词。
- 迁移时原子修复所有入站链接，不留重定向。

判断不了的规则写进评审清单，不硬做成规范。

## 维护规则表

交付时填成项目实际路径，放进根级指令或 `docs/AGENTS.md`。

| 变更 | 同时更新 |
|---|---|
| 改类型定义 | 该类型所属 L3 页面 |
| 改配置项或默认值 | 对应模块 README 的配置表 |
| 改对外行为 | 模块 README 的语义与限制；涉及取舍时加决策记录 |
| 移动或重命名文件、包 | 全部入站链接；已实现决策记录里的路径 |
| 改生成源 | 重新生成产物并提交 |
| 新增对外能力 | 模块 README、L3 参考，必要时新建决策记录 |
| 删除能力 | 所有描述该能力的文档；决策记录保留删除理由 |

## 审计清单

重复规则、历史残留（「以前是」「未来将」「待实现」）、过期状态标注、手抄目录、段落墙、死链、失效锚点、缺失入口页、双语完整性、已实现决策记录里的路径、冻结归档区、指令副本一致性。未启用的项写「不适用」并说明原因。
