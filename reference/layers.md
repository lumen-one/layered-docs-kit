# 参考：文档分层与写作规则

> 被 `00-recon`、`01-proposal`、`02-skeleton`、`03-migrate`、`05-audit` 引用。子会话只读任务卡点名的小节。

## 作用域

**受本体系约束**：面向人的文档，包括根级与子树说明、`docs/**`、每个模块/包/服务的 README、活跃决策记录、事故复盘、评审规则。

**不受本体系约束**，各自按独立规则维护：

- 代码注释与 JSDoc：契约写在声明处，由代码评审与文档检查各自约束。
- 机器消费的模板与提示词：逐字节被程序读取，改动等于改行为。
- 生成源：格式由生成器决定，只受新鲜度检查约束。
- 冻结归档区：只读，不得编辑、翻译、移动，也不得作为当前行为依据。

**指令文件分层**：根级 `AGENTS.md` 只放每次会话都需要的规则；子树（如 `packages/`、`docs/`、决策记录目录）各有一份 `AGENTS.md`，只放对该子树生效的规则。根文件不复述子树规则，子树不复述根规则。`CLAUDE.md` 是指令文件的软链接，不是第二份内容；不支持软链接的平台用同内容副本，并在提案第 5 节登记为检查项 13，两侧不一致时以 `AGENTS.md` 为准。

## 分层模型

| 层 | 位置 | 职责 | 明确不写 |
|---|---|---|---|
| L0a 根级指令 | 根 `AGENTS.md`（`CLAUDE.md` 软链接） | 每次会话都需要的规则，每条 1–3 行并链接归属页 | 教程、故事、长流程、可被链接的细节 |
| L0b 子树指令 | `packages/AGENTS.md`、`docs/AGENTS.md` 等 | 只对该子树生效的规则 | 根文件已承载的全仓规则 |
| L1 项目地图 | `docs/architecture.md` | 组成、核心模块、调用链、能力接缝、扩展点；改核心代码前必读 | 类型定义、单模块细节、决策论证、实现状态标注 |
| L2 模块契约 | 每个模块/包/服务的 `README.md` | 配置、语义、限制、扩展点、对外能力 | 其他模块的职责、生成内容与 JSDoc 的复述 |
| L3 参考手册 | `docs/reference/`，或按子系统一页组织的 `docs/subsystems/` | 类型定义、API 语义、协议、数据结构 | 行为叙事、教程步骤 |
| L4 操作手册 | `docs/cookbook/` | 编号步骤与可验证结果 | 设计论证（链接决策记录） |
| L5 决策记录 | `docs/decisions/` 或 `.agents/notes/` | 为什么、放弃了什么、如何验证 | 迁移计划、验收清单、实现步骤叙述 |
| L6 事故复盘 | `docs/postmortems/` | 事故经过与教训；本体系唯一允许事故叙事的地方 | 通用规则（提炼后放 L7） |
| L7 评审规则 | `docs/patterns/`，或按领域拆页 | 评审时执行的硬规则：必须成立什么、如何判定、谁批例外 | 类型语义、决策论证 |
| L8 生成式参考 | 源码旁或 `docs/generated/` | 由脚本生成的清单、图、表；唯一权威 | 任何手工编辑 |
| L9 站点投影 | `website/`（可选） | 把 L1–L4 投影为对外站点 | 第二份可编辑内容 |

L1 与 L3 的边界：架构页按「包/服务在系统中的角色」组织，只到职责与调用关系；类型定义、字段语义、生成 API 归 L3。项目没有独立 `docs/reference/` 时，用 `docs/subsystems/<subsystem>/README.md` 一页一个子系统，仍按 L3 规则写。

L7 的组织方式：一页通用缺陷类别，加每个 artifact 领域一页，例如服务边界、并发与生命周期、子进程与终端、持久化、客户端状态。每条规则写清「必须成立什么、怎么判定、例外由谁批」。

L8 的两种形态：同页生成区，由生成器把同一份数据写入两侧页面，两侧逐字节一致；整页生成，由生成器同时产出英文、中文与一致性记录。不存在「手工把生成结果复制到 `docs/generated/`」这第三种做法。

裁剪建议：

- 单人小项目：L0a、L1、L2，加 3 个默认检查。决策记录由提交信息与 CHANGELOG 承担，不建 L5。
- 中型项目：增加 L5、L7，以及 4 决策记录格式、5 段落内不硬换行、6 字数预算、7 引用四个检查。
- 多语言团队：增加 8 双语一致性与 9 语言切换器检查（见 `bilingual.md`）。
- 有生成物时增加 10 生成物新鲜度；11、12 保持可选。
- 有对外文档需求才引入 L9。

## 一个事实一个家

同一规则、类型、命令、默认值只在一个层级定义，其他位置链接而不复述。判断归属时问「哪一层的工作就是维护这个事实」，而不是「哪个文件最近改过它」。

发现重复时的处理顺序：确定归属页；把完整表述移到归属页；其他位置改为一句链接；若其他位置有归属页没有的细节，先把细节补进归属页再删。

## 模块 README 契约

固定顺序，前五节必检，后两节可选：

1. **Summary**：不超过 100 词，说明「读者能用它做什么」，不写内部角色或实现身份。
2. **目录**：锚点链接。
3. **快速开始**：最短可用路径、主要代价、何时该选它。
4. **配置与使用**：配置表、默认值、限制。
5. **Known Limitations**：已知限制与失败模式。
6. **开发者视角**（可选）：整体设计与数据流，精确细节链接到代码或 L3。
7. **Dev Note**（可选）：草稿、未决方向、测量数据，明确标注「非权威」。

章节结构检查只校验第 1–5 节存在且顺序正确；第 6、7 节出现时不得打乱前五节顺序。

禁止：罗列完整 API、复述 JSDoc、抄写生成目录、写其他模块的职责。

## 写作规则

每条规则都要能判定。判定不了的规则不要写进规范，写进评审清单。

| 规则 | 判定方式 | 例外审批 |
|---|---|---|
| 主文档只描述当前状态，历史与被否方案进决策记录或复盘 | 评审；用「以前」「未来将」「计划中」等特征词检索辅助 | 文档所有者 |
| 一段一个物理行，段落内不硬换行；表格、列表、代码块保持原格式 | 自动检查：段落内出现硬换行即失败 | 文档所有者，须在提案第 3 节说明替代的对齐手段 |
| 相对链接指向当前文件；历史引用用 tag 或 PR 编号，不写 commit hash | 自动检查：本地目标存在；正文出现 commit 哈希即失败 | 无 |
| 外部引用可解析 | 自动检查：组织外链接已登记（离线模式）或可访问（在线模式），格式见 `checks.md` 第 7 项 | 无 |
| 术语一词一义，首次出现给定义 | 评审清单与术语表 | 文档所有者 |
| 不用比喻替代精确名词 | 评审清单 | 文档所有者 |
| 强调有稀缺性，只有改变行为的句子加粗 | 评审清单 | 文档所有者 |
| 标题使用读者会搜索的词 | 评审清单 | 文档所有者 |
| 迁移时原子修复所有入站链接，不留重定向 | 自动检查（死链） | 无 |

## 维护规则表

交付时把这张表填成项目实际路径，并放进根级指令或 `docs/AGENTS.md`。

| 变更 | 必须同时更新 |
|---|---|
| 改类型定义 | 该类型所属 L3 页面 |
| 改配置项或默认值 | 对应模块 README 的配置表 |
| 改对外行为 | 所属模块 README 的语义与限制；决策记录（若涉及取舍） |
| 移动或重命名文件、包 | 全部入站链接；已实现决策记录中的路径与名称 |
| 改生成源 | 重新生成产物并提交 |
| 新增对外能力 | 模块 README、L3 参考、必要时新建决策记录 |
| 删除能力 | 所有描述该能力的文档；决策记录中保留删除理由 |

## 审计清单

- 重复规则：用特征短语检索，确认只有一个家。
- 历史残留：主文档中的「以前是」「未来将」「待实现」。
- 实现状态标注是否过期。
- 手抄目录是否与生成源冲突。
- 段落墙：一段承载多条规则。
- 死链、失效锚点、缺失入口页。
- 双语完整性（项目启用多语言时）。
- 已实现决策记录中的路径与当前代码一致。
- 冻结归档区未被改动，内容哈希与冻结清单一致。
- 指令文件副本一致（`CLAUDE.md` 非软链接时）。
- 新成员测试：只读 3–5 个链接页，能否重建核心架构。
