# 参考：验收与回退

> 主会话在派发前后读本节。验收标准、范围核对与回退命令的唯一来源；`INDEX.md` 与 `dispatch-templates.md` 只引用，不重复。

## 派发前基线

- `git status --short` 除 `docs-plan/state.md` 外必须为空。不干净时请用户提交或 stash；主会话不自行处理，也不得跳过该检查。`state.md` 由主会话维护，不计入子会话的写入范围；首次派发前先提交它。

## 产物验收

一个产物只有同时满足三条才算完成：

1. **存在且完整**：任务卡声明的产物存在，包含卡内「产物结构」「报告结构」或「提案结构」列出的全部必需小节。主会话只读这些结构小节，不读任务卡正文。
2. **范围未越界**：`git status --short` 的改动（除 `docs-plan/state.md`）全部落在任务写入范围内（含未跟踪的新建文件）。迁移批次的范围是：本批 `files`、`docs-plan/migrate/<batchId>.md`、报告第 3 节列出的入站链接源文件（这些文件只允许改链接目标）。
3. **未决问题已处置**：子会话回报中的未决问题为空，或已由主会话写入 `docs-plan/state.md` 的「阻塞」表并标记 `blocked`。

任一不满足就退回，不要用 `done` 跳过。连续两次失败时把失败原因交给用户，由用户决定缩小批次或调整任务卡。

## 范围核对命令

迁移批次必须执行并逐行核对，结果写入批次报告第 5 节：

```sh
git status --short
git diff --name-only
git ls-files --others --exclude-standard
git diff -- <报告第 3 节列出的入站链接源文件>
```

`git diff` 只覆盖已跟踪文件，新建文件用 `git status` 与 `git ls-files --others` 补查。入站链接源文件只允许改链接目标，报告第 3 节必须与实际 diff 一致。

其他任务只需核对 `git status --short` 的每一行都在写入范围内。

## 例外与确认点

- `recon` 验收通过后，若产物第 8 节仍有未答复的待确认项，主会话逐条询问用户，把答复追加到该项下；全部有答复后才更新状态并进入 `proposal`。
- `proposal` 第 10 节的待确认事项随「提案确认」一起询问用户，不写入阻塞表。
- 删除类批次（`deletion` 为 `true`，或 `acceptance` 含「需用户确认」）在派发前暂停，确认记录写入批次表备注后才派发。

## 失败与回退

- **子会话无产出或回报缺项**：同一 prompt 重试一次；连续两次失败后交给用户决定缩小批次、调整任务卡或换实现路径，不重复第三次。
- **产物越界**：改动尚未提交时，已跟踪文件用 `git restore -- <路径>` 回退，本任务新建的未跟踪文件直接删除。已提交时按「迁移批次出错（已经提交）」处理。
- **迁移批次出错（尚未提交）**：`git restore -- <本批已跟踪文件与报告第 3 节列出的入站链接源文件>`，删除本批新建文件，重新派发。批次报告一并删除。
- **迁移批次出错（已经提交）**：不要用 `git restore` 假装回退。经用户同意后用 `git revert <提交>` 撤销该批提交，或新建一个修复批次；处理方式写入 `state.md` 的备注。
- **用户否决提案或 `checks` 要求补项**：把意见写入「待用户确认」表的「提案确认」行，把 `proposal` 阶段改为 `in-progress`，派发提案修订任务。修订验收通过后，阶段改回 `pending`，该行改回 `待确认`，再请用户确认；用户确认后才转 `done`。
- **检查发现已完成批次失败**：把对应 `migrate` 批次改回 `pending`、`migrate` 阶段改为 `in-progress`，并在 `checks` 阶段备注写「待复跑」；`checks` 阶段保持 `done`，保证同一时间只有一个阶段是 `in-progress`。修复批次验收并提交后，按批次表重新推进 `migrate`；`migrate` 再次全部 `done` 后，把 `checks` 改为 `in-progress`、备注改为「复跑」，按 `04-checks` 的复跑模式派发，只复跑受影响检查，不重建检查器；复跑通过后把 `checks` 改回 `done` 并清空备注。已提交批次按上一条的已提交分支处理。不得直接在 `checks` 阶段改被检查文档。
- **检查无法通过且规则本身有误**：记录到 `state.md` 的阻塞表，由用户决定改规则还是改内容。不得私自删除检查项。
- **提案漏掉档位检查项**：`checks` 阶段发现提案第 5 节未覆盖档位对应的检查组合，且未写明已批准的缩减理由时，停止派发，把 `proposal` 阶段改回 `in-progress`、`checks` 改为 `pending`；按 `proposal-revise` 补齐检查项，重新确认提案后再派发 `checks`。不得由 `checks` 自行扩大范围。

## 提交

每个任务（迁移为每批）验收通过后，必须由用户提交该任务产物（用户明确授权时主会话提交）；除 `docs-plan/state.md` 外工作区干净后才派发下一个任务。
