# 参考：自动检查

能机械判定的规则才做成检查，判断类规则留给评审。这里列常见检查与扫描范围，具体实现按项目取舍。

## 扫描范围

文档检查默认扫描 git 跟踪与未忽略的 Markdown。默认排除 `.git/`、依赖目录、构建产物、生成物目录、冻结归档区和 `docs-plan/`。提案可以按项目增删排除项，写明理由即可。

## 检查清单

1. **死链与锚点**：相对链接的目标文件存在，跨页与同页 fragment 能命中目标标题；链接文字、目标路径和修复动作写进失败信息。
2. **章节结构**：模块 README 的前五节齐且顺序正确，标题按语义匹配中英文别名；决策记录按生命周期有对应章节。
3. **排版**：段落内不出现硬换行，表格、列表、代码块保持原格式；入口页和模块摘要不超项目定的字数预算。
4. **引用**：正文不写 commit hash，历史引用用 tag 或 PR 编号；组织外链接已登记或当前可访问。
5. **双语**：三件套齐全，一致性记录与当前内容对得上，结构镜像一致，切换器双向可回。
6. **生成物**：重新生成后与仓库内容逐字节一致，生成区标记完整、互不重叠。
7. **代码与注释**：文档中标记为代码的示例能编译或通过类型检查；导出有契约说明，至少覆盖参数与返回值。
8. **指令副本**：每份 `CLAUDE.md` 指向同一文件，或与对应 `AGENTS.md` 逐字节一致。

档位只是起点：`basic` 可以先做 1–3 条，`medium` 加上结构与排版，`multilingual` 再加双语；生成物、代码示例、指令副本按项目有没有对应对象决定。宁可少做几条真会失败的检查，也不要为了覆盖率做一堆不会拦人的检查。

## 实现思路

先写一个应当失败的夹具，再实现检查器，最后跑一遍确认它真的报错。失败信息让人能直接修：文件、位置、期望值、建议动作。检查器尽量独立成文件，最后接进项目现有的 test、lint 或 CI 入口，不要求开发者记新命令。

无法稳定判定的规则不要做成脚本。写成评审清单，标明适用文件、判定人和例外审批人。

不要为了变绿删规则或改被检查的文档。先判断是内容错还是上限错：内容错就修内容，上限错就调上限并写理由。
