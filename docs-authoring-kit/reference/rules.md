# 参考：规则怎么定、怎么维持

文档规则不是越全越好。新项目需要的是一组能被执行、能随项目生长的约定。

## 规则只回答四个问题

1. **谁读**：读者决定层、语气和详略。读者只有作者时，写给自己看的备忘就够；有外部使用者时，契约必须完整。
2. **哪些事实必须当家**：配置项、命令、协议、错误码、默认值、模块边界。这些每项选一个归属文件。
3. **新人从哪进**：根 README → 架构页 → 模块 README，链路要通。入口不超过三个层级。
4. **改代码时同步改哪份文档**：维护规则表回答这个。没有这张表，规则只是愿望。

四个问题都答不上来的项目，先别写规则，先把项目结构说清楚。

## 硬规则与评审项

把规则分成两类，比例大概是五条硬规则配十条评审项。

**硬规则**：能机械或一眼判断真假，违反就该拦下来。初版建议只留这些：

| 硬规则 | 判定方法 |
|---|---|
| 同一事实只在一个地方定义 | 搜索关键配置名/命令，出现两处完整表述即违反 |
| 主文档只写当前状态 | 出现「以前」「未来将」「待实现」即违反 |
| 相对链接必须可达 | 点链接或跑链接检查 |
| 移动/删除文件时同步修复入站链接 | 全仓搜索旧路径 |
| 没定的事写「待确认」 | 出现编造的结论或占位事实即违反 |

**评审项**：需要判断，不该做成脚本。例如：

- Summary 是否写清读者能做什么。
- 示例是否足够让人跑通。
- 架构页的边界划分是否符合实际。
- 是否需要图。
- 术语是否一词一义。
- 这段内容该放模块 README 还是参考页。

评审项写进 PR 清单或评审规则页，标明谁判定、例外谁批。不要为了「自动化」把评审项硬做成检查。

## 一条规则怎么写

一行规则，加一句理由或判定方法。理由比禁令更能让人在边界情况下做对判断。

好的写法：

```text
一个事实只在一个地方定义，其他位置放链接。为什么：两处各写一遍，改一处就会留下过期的另一处。
```

不好的写法：

```text
所有文档必须规范、完整、及时更新。
```

第二种无法判断真假，也无法执行。

## 维护规则表

标准档再建，放进 `AGENTS.md` 或 `docs/maintenance.md`。表里每一行是一个真实的同步动作：

| 变更 | 同时更新 |
|---|---|
| 改配置项或默认值 | 对应模块 README 的配置表 |
| 改对外行为 | 模块 README 的语义与限制；有取舍时加决策记录 |
| 新增对外能力 | 模块 README、参考页条目；必要时决策记录 |
| 删除能力 | 所有描述该能力的文档；决策记录保留删除理由 |
| 改类型定义或数据结构 | 所属参考页 |
| 移动或重命名文件、包 | 全部入站链接；已实现决策记录里的路径 |
| 改生成源 | 重新生成并提交产物 |
| 发布版本 | 变更日志、不兼容项、升级步骤 |

表里没有的行不要硬加。等真的漏了一次，再补一行。

## 提交钩子

能机械判定的规则才接进自动流程，其余留给评审。

- 先看项目已有什么：`npm test`、`make check`、pre-commit、CI。接进去，不另起一套命令。
- 早期只做两三条最容易生效的：死链、章节结构、`AGENTS.md` 与 `CLAUDE.md` 副本一致。
- 每条检查先写一个应当失败的样例，确认它真的会红，再接入口。
- 判断不了的规则不写成脚本。脚本假装覆盖，比没有检查更危险。

检查的详细思路可参考同仓库 `docs-management-kit/reference/checks.md`，但新项目不必一次做全。

## 规则怎么生长和淘汰

- 每踩到一次重复的坑，加一条；加之前先看能不能合并进已有规则。
- 每条规则记下它是为了解决什么问题。问题消失或规则没人违反也拦不住人时，删掉。
- 项目规模变化时重看规则：单人项目转多人，硬规则要补同步类；对外发布，要补契约类。
- 规则数量失控时，优先删评审项，再删硬规则里长期不生效的那条。

## 判断规则是否值得写

问一句：**这条规则不写，是否会有人犯一个真实的错？**

会，就写，并给出判定方法。不会，就不写。只为「显得专业」而存在的规则，最终都会被忽略。
