# 参考：模板

模板只给结构，不写项目内容。复制后按需删减，不要求填满每一节。

## 根 README（极简版）

````markdown
# <项目名>

一段话：它是什么、解决什么问题、给谁用。

## 快速开始

```sh
<最短可运行命令>
```

主要代价或前提：<一句话>。

## 文档

- [系统地图](docs/architecture.md)
- [模块](src/<module>/README.md)
- [决策记录](docs/decisions/)
````

入口页保持短。安装细节、配置表放模块 README，不要堆在首页。

## 架构页（一页版）

```markdown
# 架构

## 组成

| 模块 | 职责 | 边界 |
|---|---|---|
| <模块> | <它在系统里做什么> | <不负责什么> |

## 主调用链

<从入口到存储/出口的几段说明，或一张 Mermaid 图>

## 扩展点

| 扩展点 | 怎么接 | 限制 |
|---|---|---|

## 待确认

- <还没定的边界或组件>
```

只写职责和调用关系。类型、字段、完整接口放参考页。

## 模块 README（最小三节）

````markdown
# <模块名>

## Summary

一段话说明读者能用它做什么。不写内部角色或实现身份。

## 快速开始

```sh
<最短可用路径>
```

主要代价：<一句话>。什么时候该选它：<一句话>。

## 配置与限制

| 配置 | 默认值 | 取值 | 说明 |
|---|---|---|---|

已知限制：<失败模式、性能边界、不支持的情况>。
````

模块变大后再补「开发者视角」和「Dev Note」，不要一开始就写满七节。

## 模块 README（完整七节）

在最小三节之后追加：

```markdown
## 目录

- [Summary](#summary)
- [快速开始](#快速开始)
- [配置与限制](#配置与限制)

## 开发者视角

整体设计与数据流。细节链接到代码或参考页，不复述。

## Dev Note

草稿、未决方向、测量数据。开头标明「非权威」。
```

## 决策记录

提案期：

```markdown
# 决策记录：<标题>

Status: proposed

## Problem

为什么需要做这个决定。脱离方案也能读懂。

## Proposal

打算怎么做。

## Alternatives considered

**<备选方案一>**：为什么没选。
**<备选方案二>**：为什么没选。

## Acceptance criteria

怎么判断这个决定落地了。

## Risks

可能的代价与失败模式。
```

实现后：

```markdown
# 决策记录：<标题>

Status: implemented

## Problem

## Decision

用现在时写已经交付的事实。

## Alternatives considered

## Consequences

代价、限制、后续影响。
```

路径带上生命周期与类别，例如 `docs/decisions/implemented/architecture/2026-11-07-doc-rules.md`。状态编码在路径里，不再建索引。被否的记录写 `Status: rejected — <一行原因>`。

## 维护规则表

```markdown
| 变更 | 同时更新 |
|---|---|
| 改配置项或默认值 | 模块 README 配置表 |
| 改对外行为 | 模块 README 的语义与限制 |
| 改类型或数据结构 | 对应参考页 |
| 移动或重命名 | 全仓链接、已实现决策记录里的路径 |
| 删除能力 | 所有相关文档；决策记录保留理由 |
```

只写项目真实会发生的变更，不要抄全表。

## 提交前自查

```markdown
- [ ] 这次改动涉及的配置、行为、接口，文档里都有对应位置
- [ ] 新内容没有复制别处已有的完整表述
- [ ] 主文档没有历史或计划残留
- [ ] 改到的链接可点通
- [ ] 没定的事标了「待确认」
```

五条足够。超过五条就会被跳过。
