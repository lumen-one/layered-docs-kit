# 参考：从零起步的层级裁剪

迁移套件的完整分层是给存量项目用的。新项目从四层起步，出现触发条件再加层。

## 四层起步

| 层 | 位置 | 职责 | 现在建的条件 |
|---|---|---|---|
| 入口 | 根 `README.md` | 是什么、怎么跑、文档从哪进 | 总是建 |
| 系统地图 | `docs/architecture.md` | 组成、边界、主调用链、扩展点 | 有第二个模块时建；单文件项目可先并进 README |
| 模块契约 | 各模块 `README.md` | 配置、语义、限制、对外能力 | 有对外契约的模块才建 |
| 决策记录 | `docs/decisions/` | 长期取舍的理由 | 第一个真实决策出现时建记录，之前只有说明页 |

这四层覆盖了绝大多数早期项目会问的问题。其余层不预建。

## 什么时候加层

不要按「以后可能会用到」加层，按已经发生的信号加：

| 信号 | 加什么 | 加在哪 |
|---|---|---|
| 同一类事实被多个模块引用，模块 README 开始互相抄 | 参考页 | `docs/reference/` |
| 同一套操作步骤被问第二次 | 操作手册 | `docs/cookbook/` |
| 对外发布，外部读者需要更完整的语义说明 | 参考页 + 站点投影 | `docs/reference/`、站点目录 |
| 有外部贡献者或需要两种语言 | 双语配对 | 按项目语言方案 |
| 反复争论同一类设计问题 | 评审规则 | `docs/patterns/` 或对应领域页 |
| 发生需要复盘的事故 | 复盘 | `docs/postmortems/` |
| 自动检查开始有人维护 | 生成物与检查脚本 | 项目现有 CI 入口 |

加层时只加当前需要的那一层，不顺手把整套目录补齐。

## 每层的边界

- **入口**：只做导航和最短路。把安装、运行、文档地图说清，不写设计论证。
- **系统地图**：按模块在系统里的角色组织，只到职责和调用关系。类型定义、字段语义、完整 API 归参考页。
- **模块契约**：写读者用它需要知道的东西。配置表、默认值、限制、失败模式。不抄代码注释，不写别的模块的职责。
- **参考页**：一条事实一个条目。语义、约束、示例。不写教程叙事。
- **操作手册**：编号步骤和可验证结果。设计理由链接决策记录。
- **决策记录**：为什么这样选、放弃什么、代价是什么。不写实现步骤和验收清单。
- **复盘**：经过、根因、教训。通用规则提炼后再进评审页。
- **评审规则**：要成立什么、怎么判定、谁批例外。不写类型语义。
- **双语**：两种语言说的是同一件事，不设「哪种语言永远权威」。

## 最小模型的具体形态

极简档不是「少写点」，而是四个文件各司其职：

```text
README.md                 我是什么，怎么跑，接下来去哪
docs/architecture.md      系统有几块，边界在哪，谁调谁
src/<module>/README.md    这个模块能做什么，怎么配，有什么限制
docs/decisions/README.md  决策记录放哪、怎么命名、状态怎么标
```

判断一个文件该不该建，问：**它现在有唯一的读者和唯一的事实吗？** 有就建，没有就等。

## 常见过度设计

新项目最容易提前做的事：

- 一次建齐 `docs/reference/`、`docs/cookbook/`、`docs/patterns/`、`docs/postmortems/` 全套空目录。
- 为每个源文件建一份文档。
- 写一份几十页的文档规范，但没有任何人读过。
- 先写完整 API 文档，代码还没定。
- 给单模块项目画多层架构图。
- 上双语但两种语言都还没写顺。

这些都属于「为未来的可能性付费」。出现真实信号再做，成本更低。

## 与迁移套件的关系

这套层级继承迁移套件的分层思路，但只取新项目需要的最小集。项目长大后如果文档开始重复、过期、缺入口，再切到迁移套件做一次整理，不需要提前按完整分层铺好。

从零建立的规则，本质上是在为将来的迁移减少工作量：事实有唯一归属，迁移时就不用满仓找重复。
