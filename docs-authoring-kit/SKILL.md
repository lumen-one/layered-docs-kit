# 文档撰写套件（从零开始）

这套 skill 解决的是：项目还没写几行代码，文档规则该长什么样。它不生成一整套空文档，而是先定一个最小契约，再随开发逐层补。已有存量文档、需要整理迁移时，用迁移套件 `docs-management-kit`，不要用这套。

## 先判断：这次处在哪个时点

不要一上来建全套目录。先看清项目现在到哪一步，再决定做多少。

| 时点 | 做什么 |
|---|---|
| 还没开始，或刚初始化 | 走 00 定契约 → 01 搭骨架，之后按 02 日常写 |
| 写了一部分代码，文档零散 | 00 用轻量版（只补关键问题）+ 01，然后按 02 回填已有模块 |
| 只问“这个功能要不要写文档、写在哪” | 直接看 `cards/02-write.md` 的触发点表 |
| 想知道规则是不是失效了 | 走 03 轻量自查 |

默认从极简档起步。出现第二个维护者、或第一次对外发布时，再升档。

| 档位 | 产物 | 适合 |
|---|---|---|
| 极简 | 根 README、`AGENTS.md` 文档段、`docs/architecture.md` 一页、`docs/decisions/` | 个人项目、原型、早期验证 |
| 标准 | 极简 + 模块 README 契约 + 模板 + 维护规则表 | 多人协作、会被别人安装或调用 |
| 完整 | 标准 + 参考页 / 操作手册 + 双语 + 最小自动检查 | 对外产品、长期维护 |

档位不是流程要求，是取舍起点。项目只用到极简档就停在极简档，不算欠账。

## 四条硬边界

1. 不预建空层：没有内容的目录、没有对象的模板、没有读者的页面，都不建。
2. 规则少而可判定：初版硬规则控制在一屏内；判断类规则放评审清单，不硬做成规范。
3. 不替用户拍板：没定的事写「待确认」并给默认建议，不编造结论。
4. 删除、移动已有文件前先问用户；移动后同一次改完所有入站链接。

除此之外都是建议。遇到没覆盖的情况，按「读者能找到事实、同一事实只有一个家」自行判断。

## 四个阶段

| 阶段 | 任务卡 | 主要产物 | 可跳过 |
|---|---|---|---|
| 定契约 | `cards/00-charter.md` | `docs-notes/charter.md`（一页以内） | 项目极小时可口头完成 |
| 搭骨架 | `cards/01-scaffold.md` | 根 README、`AGENTS.md` 文档段、`docs/` 入口与模板 | 否 |
| 日常写 | `cards/02-write.md` | 模块 README、参考页、决策记录、同步改动 | 否，长期重复执行 |
| 自查与升级 | `cards/03-review.md` | 检查结论、升级建议 | 可，按需 |

每阶段开始前读对应任务卡。卡里已经写了目标、输入、产物和完成标准。`docs-notes/` 是过程目录，只放还没定稿的东西；定稿后要么并入 `docs/`，要么删掉。

## 每个阶段怎么收尾

- 产物写到卡里指定的路径，优先写进项目真实文档，不另起一套。
- 对照卡内「完成标准」自查，没做到的在回报里说清楚。
- 向用户回报：产物路径、没定的事、建议的下一步。定契约阶段还要回报你替他做的默认选择。
- 阶段完成由用户提交；用户明确授权时才代提交。
- 顺带记一笔规则摩擦：这次有没有规则冲突、被迫绕开、没覆盖、或引用了失效事实。有就追加到 `docs-notes/rule-signals.md`，只记录不决策；判断方法见 `reference/rule-evolution.md`。

## 写规则时记住三件事

- 规则写进 `AGENTS.md` 或项目根级指令，不写进没人读的长篇 `CONTRIBUTING.md`。每次会话都会读到的地方才有效。
- 每条硬规则一句，带判定方法或反例；解释「为什么」比堆「禁止」更能让人遵守。
- 规则会失效。每次踩到重复的坑就加一条，定期删掉没人违反也拦不住人的条款。只增不减的规则集很快会被忽略。怎么记摩擦、什么时候改，见 `reference/rule-evolution.md`。

## 派发子会话

上下文紧张时，主会话只读本文件和 `docs-notes/charter.md`，一次派一个阶段。子会话提示词：

```text
你是「文档规则建立」的子会话，任务：<阶段名>。
项目根：<绝对路径>
skill 目录：<本 skill 的绝对路径>
任务卡：<skill 目录>/cards/<阶段卡>.md

读：任务卡本身，以及卡内「输入」列出的文件。
写：卡内「产物」列出的路径，其他文件不动。

完成后回报：产物路径；哪几条完成标准没做到；需要我决定的事。
```

## 判断标准

做得好不好，看四件事：

- 新成员只读根 README 和架构页，能跑起来，并知道去哪改文档。
- 改一个配置项或行为，知道要在哪份文档补哪一行。
- 硬规则能被一眼判定真假，评审项有明确的判定人。
- 没有任何为「以后可能用到」而建的空目录和空模板。
