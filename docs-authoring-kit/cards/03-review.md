# 任务卡 03：自查与升级

## 目标

用很少的时间确认规则还在生效，并判断要不要升档。不是全量审计，不追求把所有问题一次修完。

## 输入

- 根 README、`AGENTS.md` 文档段、`docs/architecture.md`、`docs/decisions/`。
- 当前模块数量、维护人数、是否已对外发布。
- `reference/rules.md` 的「规则怎么生长和淘汰」与「提交钩子」。

## 做法

按下面几项各看一眼，每项给一个结论：通过、有问题、不适用。没问题就直接写通过，不要为了显得认真而找问题。

| 检查项 | 怎么看 | 有问题时 |
|---|---|---|
| 新人路径 | 从根 README 出发，能否走到架构页和所有模块 README | 补链接或补一段摘要 |
| 事实归属 | 搜索一个配置名或命令，是否在多处各写了一遍 | 选一个归属页，别处改成链接 |
| 历史残留 | 主文档里是否还有「以前」「未来将」「待实现」 | 移到决策记录或删掉 |
| 死链 | 抽点相对链接，或跑项目已有的链接检查 | 修链接；没有工具就人工过入口页 |
| 规则可判定 | 硬规则是否每条都能一眼判断真假 | 判断不了的移进评审清单 |
| 空层与空模板 | 是否有没内容的目录、没人用的模板 | 删掉；删除前问用户 |

一次只修一类问题。其余记下来，下次再处理，不在自查阶段做大规模重写。

## 升级信号

出现下面任一情况，建议升档而不是继续在极简档打补丁：

- 有第二个人开始维护 → 标准档：补模块 README 契约、模板、维护规则表。
- 第一次对外发布 → 完整档：补参考页、操作手册；有外部贡献者再加双语与自动检查。
- 同一类问题反复出现 → 加一条硬规则或一个检查，而不是每次口头提醒。
- 模块多到一页架构图放不下 → 拆子系统页，架构页只留导航与边界。
- 规则已经没人遵守 → 先删规则，再谈执行；留着不执行的规则比没有更糟。

## 产物

- 口头回报即可；需要留档时写 `docs-notes/review.md`，一页以内：

```markdown
# 文档规则自查

## 结论
| 检查项 | 结论 | 证据或处置 |
## 升级建议
| 信号 | 是否出现 | 建议动作 |
## 未处理
| 问题 | 为什么先不处理 | 什么时候再看 |
```

## 完成标准

- 每项检查都有结论，通过的项写通过，不写「整体感觉良好」。
- 升级建议有触发条件，不是凭感觉说「应该更规范」。
- 实际修改控制在一类问题内，其余进入未处理清单。
