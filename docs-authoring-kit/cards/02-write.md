# 任务卡 02：日常写

## 目标

开发过程中按触发点写文档，不攒到最后。每次只写当次改动需要的那几段，写完就能用。

## 输入

- `AGENTS.md` 的文档段与维护规则表。
- `reference/templates.md` 里对应的模板。
- 本次改动的代码、配置、接口或目录变化。
- 需要的决策记录格式，见 `reference/templates.md`。

## 触发点表

先判断这次改动落不落进下表。落不进就不写，落进了就写指定位置，不额外扩写。

| 什么时候 | 写什么 | 放哪 | 最小形态 |
|---|---|---|---|
| 新建一个有对外契约的模块 | 一句话 Summary、快速开始、已知限制 | 模块 `README.md` | 三节；超过三个二级主题再拆参考页 |
| 新增或修改配置项 | 名称、默认值、取值范围、影响 | 模块 README 的配置表 | 一行 |
| 新增对外 API、协议、错误码、数据结构 | 语义、约束、一个例子 | `docs/reference/` 或子系统页 | 一个条目 |
| 做了有长期影响的取舍 | 问题、决定、备选方案、代价 | `docs/decisions/` | 一条记录 |
| 改变对外行为 | 更新语义与限制；有取舍就加决策记录 | 模块 README | 改现有段落，不新开页 |
| 移动或重命名目录、包 | 修复全部入站链接与已实现记录里的路径 | 全仓 | 同一次改完 |
| 同一步骤被问第二次 | 编号步骤与可验证结果 | `docs/cookbook/` | 一页 |
| 发生事故 | 经过、根因、教训 | `docs/postmortems/` | 一页；通用规则提炼后再进评审页 |
| 发布新版本 | 变更条目、不兼容项、升级步骤 | 项目已有的 changelog / 发布说明 | 跟项目现有格式 |

发布版本时顺带跑一次 `03-review.md` 的检查：账本结算、升级信号各看一眼。不另设复审日历。

## 文档先行还是事后补

- 值得先写：对外契约（别人要按它开发）、有取舍的决策。先写能少返工。
- 不值得先写：模块 README、教程、架构页。没有代码时写出来是空壳，等首个可用版本同批提交。
- 不写「未来计划」页。计划放 issue 或决策记录的 `proposed` 状态里，不占主文档。

## 每类文档的边界

- **模块 README**：Summary 写读者能做什么，不写内部角色；配置表写默认值与限制；不抄完整 API、不复述代码注释、不写别的模块职责。
- **架构页**：按模块在系统里的角色组织，只到职责与调用关系；类型与字段语义放参考页。
- **参考页**：一条事实一个条目，写语义、约束、示例；不写教程叙事。
- **决策记录**：动机能脱离方案读懂；备选方案写真实落选原因，不事后编造；实现后把状态与路径一起改成 `implemented`。
- **操作手册**：编号步骤，每步有可验证结果；设计理由链接决策记录，不展开论证。

## 写完自查

- 这次改动涉及的每个事实，都能指出唯一的归属文件。
- 新增内容没有复制别处已有的表述，需要时只放链接。
- 主文档里没有「以前是」「未来将」「待实现」这类历史或计划残留。
- 改到的链接都点得通；移动文件时全仓搜过旧路径。

## 完成标准

- 每个触发点都处理了：写了，或明确判断不需要写并说明理由。
- 没有留下「以后补」的占位段落。
- 改动范围只在本模块文档、对应参考页/决策记录和必要的链接修复内。
