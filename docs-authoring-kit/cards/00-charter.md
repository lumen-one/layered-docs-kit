# 任务卡 00：定契约

## 目标

用最少的问题定下文档契约：谁读、哪些事实要当家、启用哪几层、规则写在哪。产出一页纸，不是一本规范手册。

## 输入

- 项目形态：库、服务、CLI、应用、插件、单仓多包；是否对外分发。
- 读者：只有作者自己、团队、外部使用者、贡献者，可能同时有。
- 已存在的代码与目录；空项目就按预期形态判断。
- 语言要求：单语还是双语，团队用什么语言沟通。
- 预期寿命与维护人数；说不清就按「可能长期、目前一人」处理。

## 做法

一次问完下面四个问题，每个都给默认值。用户没答或说「你定」时，按默认值写进契约，并在「待确认」里标出来，不反复追问。

1. **谁会读这份文档？** 默认：作者 + 未来接手的人。
2. **哪些事实最容易被问起或写错？** 默认：怎么装、怎么跑、配置项与默认值、模块边界。
3. **文档和代码放一起还是分开？** 默认：同仓库，文档挨着代码。
4. **用什么语言写？** 默认：团队沟通语言，单语。

再补一个判断：**现在需要几层？** 默认只启用四层——入口、系统地图、模块契约、决策记录。其余层等出现触发条件再加，见 `reference/layering.md`。

## 产物

`docs-notes/charter.md`，控制在一页内，建议包含：

```markdown
# 文档契约：<项目名>

## 1. 读者
| 读者 | 他们最想解决什么 | 从哪进 |
## 2. 关键事实
| 事实 | 归属文件 | 其他位置只放 |
## 3. 启用层级
| 层 | 位置 | 现在建还是等触发 |
## 4. 语言与位置
单语 / 双语；文档与代码同仓还是分离
## 5. 硬规则初稿
不超过五条，每条一句，能一眼判定
## 6. 待确认
| 问题 | 我暂时按什么处理 | 什么时候需要你定 |
```

## 最小模型长什么样

极简档只有四个东西，各自一句话职责：

| 文件 | 职责 | 不写 |
|---|---|---|
| 根 `README.md` | 这是什么、怎么跑起来、文档从哪进 | 设计论证、完整 API |
| `docs/architecture.md` | 系统由哪几块组成、边界与主调用链 | 类型定义、单模块细节 |
| 模块 `README.md` | 该模块对外能做什么、配置与限制 | 别的模块的职责、代码注释复述 |
| `docs/decisions/` | 长期取舍的理由 | 实现步骤、验收清单 |

有代码的模块才建 README；没有模块就先不建。参考页、操作手册、复盘、评审规则都不在最小模型里。

## 完成标准

- 四个问题都有答案或明确的默认值，没有悬空的「看情况」。
- 关键事实表里每一项都有唯一归属文件。
- 硬规则不超过五条，每条都能用一句话判断真假。
- 契约能在一页内读完；超过一页说明把规范细节写早了，删回一页。
