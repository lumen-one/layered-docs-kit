# 文档管理套件

把项目的文档从“能写就行”带到“读者能找到、维护者知道往哪写”。

这套 skill 不是一次性文档生成器，而是一组可裁剪的任务卡：先看现状，再给方案，然后按项目需要挑阶段执行。单会话能做，拆成主会话加子会话也能做。方法按项目取舍，这里只写目标、输入、产物和边界。

## 先判断：这次要做多少

不要一上来跑全流程。先花几分钟看现场，再给用户一个明确建议。

看这些：

- 根 README、`docs/`、模块 README 的存量和质量。
- 代码模块边界、构建与 CI 入口。
- 读者是谁、有没有多语言要求。
- 本次是想“先跑通”，还是“长期维护”。

然后给三档建议，默认推荐标准版：

| 档位 | 包含阶段 | 适合 |
|---|---|---|
| 快速版 | 00 现状评估 → 01 架构提案 → 02 层级与规则 | 文档少，想先立骨架 |
| 标准版 | 00–05 全流程，迁移按批 | 有存量文档，需要真正整理 |
| 深度版 | 标准版 + 决策记录 + 双语 + 自动检查 | 长期维护、多人协作、对外文档 |

裁剪是正常的：没有存量文档就跳过 03；用户明确不要自动检查就跳过 04，把评审清单放进交付物。阶段顺序通常如此，但不必为了流程完整而做无用功。

## 四条硬边界

1. 只改当前阶段允许的路径，范围外文件不动。
2. 删除文件或目录前先问用户。
3. 不编造证据、结论或文件内容；写不出证据就写「待确认」。
4. 需要用户决策时停下来问，不自行假设。

除此之外都是建议。遇到本 skill 没覆盖的情况，按“读者能找到事实、同一事实只有一个家”的目标自行判断。

## 六阶段

| 阶段 | 任务卡 | 主要产物 | 可跳过 |
|---|---|---|---|
| 现状评估 | `cards/00-recon.md` | `docs-plan/recon.md` | 否 |
| 架构提案 | `cards/01-proposal.md` | `docs-plan/proposal.md`、批次清单 | 否 |
| 层级与规则 | `cards/02-skeleton.md` | 项目内层级、模板、指令文件、`docs-plan/skeleton-report.md` | 否 |
| 迁移 | `cards/03-migrate.md` | 批次内文档、`docs-plan/migrate/<批次>.md` | 无存量时 |
| 自动检查 | `cards/04-checks.md` | 检查脚本与夹具、`docs-plan/checks-report.md` | 可，需用户同意 |
| 审计与交付 | `cards/05-audit.md` | `docs-plan/audit-report.md`、五项交付物 | 否 |

每阶段开始前读对应任务卡。卡里已经写了目标、输入、产物和完成标准，不需要另加流程说明。卡内“输入”列出的 reference 和前置产物按需读，不要一次全读。

## 每个阶段怎么收尾

- 产物写到卡里指定的路径，过程产物统一放 `docs-plan/`。
- 对照卡内“完成标准”自查，没做到的在回报里说清楚。
- 把产物路径和一句备注写进 `docs-plan/state.md`（模板见 `state-template.md`）。
- 向用户回报：产物路径、未达标项、需要用户决定的事、建议下一步。
- 阶段完成由用户提交；用户明确授权时才代提交。
- 顺带记一笔规则摩擦：这次有没有规则冲突、被迫绕开、没覆盖、或引用了失效事实。有就追加到 `docs-plan/rule-signals.md`，只记录不决策；判断方法见 `reference/rule-evolution.md`。

## 派发子会话

上下文紧张或阶段之间需要隔离时，主会话只读本文件和 `docs-plan/state.md`，一次派一个阶段。子会话提示词：

```text
你是「文档体系建立」的子会话，任务：<阶段名>。
项目根：<绝对路径>
skill 目录：<本 skill 的绝对路径>
任务卡：<skill 目录>/cards/<阶段卡>.md

读：任务卡本身，以及卡内「输入」列出的参考与前置产物。
写：卡内「产物」列出的路径，其他文件不动。

完成后回报：产物路径；哪几条完成标准没做到；需要我决定的事。
```

没有子代理时，开新会话粘贴上面这段即可。只能单会话时，按阶段顺序自己执行，每阶段结束对照完成标准自查。上下文接近上限时，把当前产物和未决问题写进 `docs-plan/`，新会话读 `state.md` 继续。

## 交付物

审计阶段收尾时，确保这五项都有路径且能直接读：

1. 文档架构说明。
2. 迁移报告（没有迁移就写「无存量迁移」）。
3. 检查使用说明（跳过检查时为评审清单）。
4. 维护规则表。
5. 遗留问题清单。

## 判断标准

做得好不好，看三件事：

- 读者从少数入口能不能找到需要的事实。
- 同一事实是不是只有一个归属页。
- 下一个人改代码时，是否知道该同步改哪份文档。

层级多少、批次多大、要不要双语，都按项目定。不追求一步到位，先跑通再加。
