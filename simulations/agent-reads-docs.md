# 模拟：Agent 读到 skill 建立后的文档，会怎么走

这份文档不复述 skill 的流程，而是把场景固定下来，推演一个新会话的 Agent 在**不重新加载 skill** 的情况下，只靠项目里已经建好的文档，完成一次真实改动。

结论先放这里：Agent 不是按「入口 → 系统地图 → 模块契约 → 决策记录」的层级顺序读的，而是按「任务关键词 → 入口 → 命中的模块 → 按需补边界」走的。层级是写的时候的归属结构，不是读的时候的检索结构。

图表单独放在 `agent-reads-docs-flow.md`。

## 一、场景固定

样例项目叫 `taskq`：一个本地任务队列 CLI，按优先级执行 shell 任务，失败可重试，状态存本地 SQLite。

它按撰写套件的极简档建了文档，产物是：

```text
taskq/
  README.md
  AGENTS.md
  docs/
    architecture.md
    decisions/
      README.md
      implemented/architecture/2026-10-12-storage-choice.md
  src/
    cli/README.md
    queue/README.md
```

注意这里没有 `docs/reference/`、`docs/cookbook/`、`docs/postmortems/`，也没有模板目录。极简档不建这些，是设计选择，不是欠账。

给 Agent 的任务是：

> 给 taskq 加 `maxRetries` 配置，默认 5，允许 0–10；失败重试改成指数退避（1s、2s、4s…）；`--max-retries` 要能覆盖配置文件。

这个任务同时命中三个触发点：新增配置项、改变对外行为、有长期取舍。

## 二、Agent 实际读的顺序

| # | 读什么 | 为什么读 | 读到什么 | 据此决定 |
|---|---|---|---|---|
| 0 | `AGENTS.md` 文档段 | 会话启动自动注入，不需要主动找 | 入口、5 条硬规则、触发点 | 这次要写三处：配置表、语义段、决策记录 |
| 1 | `README.md` | 入口 | 项目是什么、怎么跑、文档地图四条链接 | 任务属于 queue，architecture 先不读 |
| 2 | `src/queue/README.md` | 文档地图指向 | 配置表、重试语义、已知限制 | 发现已经有 `retry_limit`，不能直接加第二个同义配置 |
| 3 | `docs/architecture.md` | 要改重试逻辑，需要确认模块边界 | 三块职责、主调用链、queue 不负责什么 | 退避计算属于 queue，不写进 store |
| 4 | `docs/decisions/README.md` | 这次有取舍要留档 | 路径格式、状态取值 | 记录落到 `implemented/architecture/` |
| 5 | 一条已有决策记录 | 确认章节格式 | Problem / Decision / Alternatives / Consequences | 照这个结构写 |
| 6 | 代码 | 实现 | 配置 schema、重试计算、CLI 参数解析 | 改三处，并保留旧配置兼容 |
| 7 | 回写文档 | 触发点 | — | 改配置表、语义段、限制段，新增决策记录 |
| 8 | 五条提交前自查 | 收尾 | — | 逐条过 |
| 9 | `docs-notes/rule-signals.md` | 记录摩擦 | — | 记一条「决策格式靠样本推断」 |

两个值得注意的地方：

- 第 0 步是零成本的。Agent 没有「先决定读哪份文档」这一步，规则和入口是随会话一起进来的。这就是 skill 坚持把规则写进 `AGENTS.md`、而不是 `CONTRIBUTING.md` 的原因。
- 第 3 步不是必读。如果任务只是改一句文案，Agent 读完 queue README 就够了。architecture 是被「要动调用链」这个信号拉进来的，不是每次都读。

## 三、完整推演

### 第 0 步：会话启动，读到 AGENTS.md

Agent 看到的是这样一段（一屏内）：

> ## 文档
>
> - 文档入口：`README.md` → `docs/architecture.md` → 各模块 `README.md`。
> - 一个事实只在一个地方定义，其他位置放链接。
> - 主文档只写当前状态；历史与取舍进 `docs/decisions/`。
> - 改配置、对外行为、目录或包名时，同一次改动更新对应文档。
> - 定不下来的事写「待确认」，不要编。
> - 触发点：新配置 → 模块 README 配置表；对外行为 → 模块 README 语义与限制；长期取舍 → `docs/decisions/`；移动目录 → 全仓链接。

Agent 的判断是：这个任务落在三个触发点上，不是「改完代码再说」。注意它还**没有读任何项目文档**，但已经知道要往哪三处写。这是整套设计里最值钱的一步。

### 第 1 步：读根 README

README 很短：一句话说明、一条快速开始、四条文档链接。

Agent 的判断是：任务涉及 queue，直接进 `src/queue/README.md`。architecture 先放着，因为还不知道要不要动跨模块边界。

### 第 2 步：读 queue 模块 README

配置表里有一行：

> | 配置 | 默认值 | 取值 | 说明 |
> |---|---|---|---|
> | `retry_limit` | 3 | 0–10 | 失败任务最大重试次数 |
> | `retry_interval` | 1s | 1s–60s | 重试间隔，固定值 |

语义段写着：失败任务按固定间隔重试，超过 `retry_limit` 后标记为 failed。

Agent 在这里做了一个任务描述里没说的判断：**`maxRetries` 和已有的 `retry_limit` 是同一个事实。** 直接新增会变成两个配置管一件事，违反「一个事实只在一个地方定义」。

它的处理是：

- 把 `retry_limit` 正式改名为 `maxRetries`，保留旧名读取兼容，标 `deprecated`。
- 「是否在 2.0 彻底移除旧名」写进「待确认」，不替用户拍板。

这一步是文档在真正起作用：如果配置表没写默认值和取值范围，Agent 会去代码里翻，翻完还要猜哪些是对外契约。

### 第 3 步：读 architecture

Agent 只读「组成」和「主调用链」两节：

> - cli：解析参数、组装配置、调用 queue。
> - queue：入队、调度、失败重试。
> - store：持久化任务与状态。
>
> 主调用链：cli → queue.enqueue → store.persist；queue.worker → store.claim → run。
>
> 边界：queue 不负责任务内容，只负责调度与重试。

Agent 的判断是：退避计算属于 queue 的职责，不该下沉到 store。所以它没有去读 `src/store/`，也没有改持久化层。

这一步说明架构页的正确用法：它不是给人看的全景图，是给 Agent 划「这次不该碰哪」的边界。

### 第 4–5 步：决策记录的写前确认

`docs/decisions/README.md` 给了路径格式和状态取值：

> 路径：`docs/decisions/<status>/<category>/<YYYY-MM-DD>-<slug>.md`
>
> 状态：`proposed`、`implemented`、`rejected`

Agent 再翻一条已有记录，确认正文是四节：Problem、Decision、Alternatives considered、Consequences。

它的判断是：这次取舍已经落地，直接写 `implemented`，不先写 `proposed` 再改状态。

### 第 6 步：改代码

三处改动：

- 配置 schema 加 `maxRetries`，校验 0–10，默认 5。
- 重试间隔从固定值改成 `1s × 2^n`，上限 30s。
- CLI 的 `--max-retries` 优先级高于配置文件。

旧配置 `retry_limit` 读取时映射到 `maxRetries`，并在日志里提示已弃用。

### 第 7 步：回写文档

按触发点，只动三处：

| 触发点 | 写在哪 | 改成什么 |
|---|---|---|
| 新增配置项 | queue README 配置表 | `maxRetries` 一行；`retry_limit` 标 deprecated |
| 改变对外行为 | queue README 语义段 | 固定间隔改为指数退避，写清上限 30s |
| 长期取舍 | 新建决策记录 | 为什么选指数退避、放弃哪些方案、代价是什么 |

没动的：根 README（入口没变）、architecture（职责没变）、cli README（参数透传，语义仍以 queue 为准）。

决策记录里写：

- Problem：固定间隔在依赖服务恢复慢时会造成同步重试风暴。
- Decision：指数退避，1s 起，封顶 30s。
- Alternatives：固定间隔（简单，但恢复期压力大）、指数加抖动（更适合多客户端，本工具单机运行，收益低）、线性增长（长尾恢复慢）。
- Consequences：长尾任务恢复时间变长；重试计数仍不持久化，进程重启会丢。

最后一条是主动写进「限制」的，不是藏起来。这是 skill 里「已知限制」那一节的实际价值。

### 第 8 步：五条提交前自查

1. 配置、行为、接口都有对应位置：通过。
2. 新内容没有复制别处已有的完整表述：通过，architecture 只留职责，没有抄配置表。
3. 主文档没有历史或计划残留：通过，「以前是固定间隔」只出现在决策记录里。
4. 改到的链接可点通：通过，路径没有移动。
5. 没定的事标了「待确认」：通过，旧配置何时移除已标。

### 第 9 步：摩擦记账

Agent 记了一条：

> 日期：2026-11-07
> 信号：规则空白
> 卡在哪：`docs/decisions/README.md` 只写了路径和状态，没写正文有哪几节，只能靠翻样本推断。
> 当时处理：照已有记录的四节写。
> 候选动作：在 `decisions/README.md` 补三行章节清单。

按规则演化的约定，这一步只记录不决策。等 03 自查结算时，同类信号出现第二次，再决定要不要补。

## 四、文档在哪些点上真的帮上了忙

不是所有文档都同等有用。这次推演里，真正改变 Agent 行为的是四个点：

1. **`AGENTS.md` 的触发点**：让 Agent 在动手前就知道要写三处，而不是提交前才想起来。
2. **queue README 的配置表**：暴露出 `retry_limit` 已存在，避免造出第二个同义配置。
3. **architecture 的边界列**：明确 queue 不负责什么，阻止改动扩散到 store。
4. **decisions 的路径与状态**：让记录可被下一次会话按路径找到，不需要索引。

反过来说，architecture 的「扩展点」一节这次完全没用到。它没有错，只是这个任务不需要。文档允许「这次不读」，是健康状态。

## 五、一个真实断点（已补）：极简档的 `AGENTS.md` 示例少了触发点

这是这次推演里唯一发现的硬缺口，值得单独说。

2026-11-07 已补进 `cards/01-scaffold.md` 的示例骨架：触发点一行、升级信号一行。下面的 A/B 对比保留，用来说明这两行为什么不是可选项。

`cards/01-scaffold.md` 的「做法」第 2 条要求 `AGENTS.md` 写「硬规则、维护规则表指针、日常写文档的触发点」。但它当时给的示例骨架只有 5 条硬规则和一句「维护规则表：见 `docs/maintenance.md`（标准档再建）」，**没有触发点**。

于是极简档会出现两个版本的文档，Agent 的行为差一截：

| 行为 | A 版：照示例骨架写 | B 版：按做法补了触发点 |
|---|---|---|
| 知道要改配置表 | 不一定，靠硬规则「改配置时更新对应文档」推断 | 知道，触发点直接写「新配置 → 模块 README 配置表」 |
| 发现已有 `retry_limit` | 可能直接新增 `maxRetries`，造成两个同义配置 | 会先看配置表，倾向复用 |
| 写决策记录 | 大概率不写，极简档没有维护规则表提醒 | 会写，触发点写了「长期取舍 → decisions」 |
| 结果 | 代码改了，文档只跟上一部分 | 三处同步，决策可追溯 |

原因不复杂：极简档没有 `docs/maintenance.md`，示例又把触发点省了，那「日常写」这一阶段的依据就只剩 skill 里的 `cards/02-write.md`。可下一次会话的 Agent 不一定会重新加载 skill。**文档建立之后，skill 就不在场了，项目文档必须自己站住。**

我的判断：这不是设计理念的问题，是示例和做法不一致。当时的改法只需要在示例骨架里补两行：

> - 触发点：新配置 → 模块 README 配置表；对外行为 → 模块 README 语义与限制；长期取舍 → `docs/decisions/`；移动目录 → 全仓链接。
> - 升级信号：出现第二维护者、首次对外发布、同一事实开始两处各写、模块多到一页放不下时，回撰写套件走一次 03 自查。

两行，不增加层级，不破坏「一屏内」。这也符合「规则少而可判定」——四个触发点和四个升级信号都能一眼对照，不是模糊要求。

## 六、任务 B：移动目录时的一个边界

再推一个任务：把 `src/queue` 重命名为 `src/worker`。

Agent 按 `AGENTS.md` 的硬规则「移动文件时同步修复入站链接」，全仓搜旧路径，找到四处：

1. 根 README 的文档地图。
2. architecture 组成表里的模块名。
3. `src/queue/README.md` 自身的位置。
4. 一条已实现决策记录里写的路径。

前三处没有争议，同一次改完。第四处有一个语义张力：决策记录是历史事实，正文里如果写着「当时把队列放在 `src/queue`」，直接改路径会让记录失真；不改又点不通。

我的判断是区分两种路径：

- **链接**：必须修，否则读者点不通。
- **叙述里的历史路径**：保留原样，或写成「原 `src/queue`，现 `src/worker`」，不改写历史。

skill 现在写的是「已实现决策记录里的路径」要修，没有区分这两者。这是一处值得补一句的边界，不是错误。补法也不用长篇：

> 决策记录里的链接跟着改；正文叙述的历史路径保留，必要时注明现路径。

## 七、结论

1. **skill 建立的不是文档集合，是 Agent 的默认路由和触发点。** 文档质量不看写得多全，看 Agent 不加载 skill 时能不能走对。
2. **最关键的文件是 `AGENTS.md` 那一屏，不是 architecture。** 它决定 Agent 是否知道「这次要写文档」。architecture 决定的是「改动别越界」。
3. **读取是任务驱动的，层级是按需展开的。** 简单任务只读两层，跨模块任务才会拉进 architecture 和 decisions。这不是文档没写好，是设计本来就不要求每次读全套。
4. **极简档有一个真实断点：示例骨架缺触发点。** 补一行即可，不影响档位设计。
5. **移动目录的规则值得区分「链接」和「历史叙述」。** 现在两者混在一起，实际执行时会让人犹豫。

如果只做一件事，我建议先补第 4 条。它影响的是每一次日常改动，而不只是偶尔发生的目录重命名。
